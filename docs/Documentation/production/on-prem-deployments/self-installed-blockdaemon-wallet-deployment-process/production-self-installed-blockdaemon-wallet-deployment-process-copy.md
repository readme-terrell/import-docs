# High-level sequence

![](https://files.readme.io/0394c33-b12cecf4-9a47-4543-8f22-89bde62f4d59.png)

The AWS deployment of the Self-installed Blockdaemon Wallet involves distinct, secure setup steps with multi-account partitioning for true isolation. Separate privileged actors deploy components into different AWS Accounts with separate AWS KMS policies and Secret Manager instances. During execution, sensitive data is protected within Nitro enclaves. This ensures no single party has direct or indirect access to multiple master key shards.

> 📘 **Note**:
>
> At this time, the automated deployment is packaged exclusively for AWS.

## Step 1: Send the request form to the sales team

1. To obtain the request form, [Contact Us](mailto:sales@blockdaemon.com) or go to this [page](https://blockdaemon.com/get-in-touch/) and enter your contact details. 
2. Our sales team will send you a deployment request form which includes more detailed information including but not limited to:
   1. A DNS zone that will be used for your hosted wallet. Example: [https://wallet.](https://wallet.)`<subdomain>`.`<companydomain.com>`. The wallet installer will create networking services within this zone. Furthermore, the authentication service will call back to this domain endpoint.
   2. The three new AWS Account IDs that will be used for the installation. The 12-digit AWS identifiers are used to assign permissions to pull container images from the Blockdaemon AWS EC2 Container Registry repository.
3. To initiate the process, please complete the form and send it back to us.

## Step 2: Configure identity provider

The wallet relies on an external Open ID Connect (OIDC) authentication service to verify user identities and provide secure access tokens to the wallet. If you do not have an existing OIDC authentication service, speak to our sales team about running one for you.

1. Register both a Native App and Single-Page App application within the identity provider (IdP).
2. Provide application details (name, redirect URIs, origins).
3. Obtain generated Application Client ID and Secret.
4. Set up any required scopes and claims.
5. Note the following values which are to be used by the wallet
   1. OIDC Native App ClientID (Institutional Wallet Approver App)
   2. OIDC Single-Page App ClientID (Wallet UI)
   3. OIDC Audience
   4. OIDC Issuer

## Step 3: Generate customer tokens

We will generate tokens granting access to the various supporting services. These will be sent to you via a secure channel. The supporting services include:

1. Apple Push Notification signing key
2. Crypto token rates key

## Step 4: Receive deployment info

You will receive all deployment information via a secure channel, including:

1. Access tokens
2. Installation software repository details

## Step 5: Generate Ubiquity API key

You will generate your own Ubiquity API key by following the instructions provided [here](https://blockdaemon.com/documentation/ubiquity-api/authentication/#api-key). The Wallet uses the Ubiquity API to query and broadcast transactions to the different blockchain networks.

## Step 6: Perform Key Ceremony (privileged actors)

### 3x Encryptor Master Passwords

The Encryptor Master Password is highly sensitive as it encrypts the MPA node’s database containing the wallet’s master key share. For every MPA node there must be a corresponding Encryptor Master Password. Prior to deployment, the Encryptor Master Password for each database must be generated by a different privileged actor. Each actor then executes the seeding process, by launching the Configurator tool and supplying the Encryptor Master Password as input. The tool encrypts and uploads the Encrypted Master Password to the corresponding AWS SecretManger vault. The privileged actors must follow the company policy with regards to key ceremony.

### 1x Emergency Recovery Secret

In the event of a disaster, the ERS key-pair is used to back up and restore the master private key of the wallet. The backup is encrypted with the public key of the ERS key-pair. This ERS private key must be generated by a single privileged actor and stored securely. The privileged actor should follow the company policy when performing the key ceremonies. For more information, refer to the ERS Backup and Recovery user guide. The base64 encoded output of the public key must be supplied during the application installation of the wallet.

## Step 7: Perform Key Ceremony seeding (privileged actors)

Each privileged actor will carry out the key ceremony seeding to encrypt and upload the previously generated Encryptor Master Password keys to AWS SecretManager (steps 1, 2, and 3 of the below sequence):

### Prerequisites:

Before carrying out the key ceremony, ensure that you have the following tools and have verified the authenticity of the software:

* Docker - [https://docs.docker.com/get-docker/](https://docs.docker.com/get-docker/) 
* Cosign - [https://docs.sigstore.dev/cosign/installation/](https://docs.sigstore.dev/cosign/installation/) 
* New AWS Account details:
  * AWS Account ID
  * AWS Region
  * AWS credentials

Use your AWS credentials to authenticate to the Blockdaemon container registry repository:

```
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin \
638663786504.dkr.ecr.us-east-1.amazonaws.com
```

Use the `cosign` executable to validate the authenticity of the images against the Blockdaemon signing authority. Do this for every image: \[approval-service, configurator, docs, facade, installer, policy-node, wallet]

### Execution Steps

1. Each of the 3 Privileged Actors perform the EncrypterMasterPassword seeding to AWS infrastructure for each MPA node
   1. The Key Ceremony and Seeder process will execute performing the following actions:
      1. Capture the EncrypterMasterPassword for the corresponding MPA node as input.
      2. Instantiate the AWS KMS policies and SecretsManager vaults.
      3. Create an IAM administrator roles for the later installations of remaining compute infrastructure and applications.
      4. Encrypt and upload the EncrypterMasterPassword to SecretsManager.
   2. Executing the Configurator seeding will interactively request the following inputs:
      1. Deployment environment=production
      2. Execution phase=key ceremony seeding
      3. MPA node number=\[1,2,3]
      4. Infrastructure provider=AWS
      5. New AWS Account ID and region
      6. AWS Account ID of the existing administration account that will manage the application
   3. Execute the following to seed and output the generated configuration locally:
      1. ```
         $ docker run -it -v $(pwd):/conf 638663786504.dkr.ecr.us-east-1.amazonaws.com/blockdaemon/wallet/configurator:1.0.0  
         ...
         ```

## Step 8: Execute the application installations (administrator)

You will carry out the application installation by following Steps 4, 5, and 6 of the below sequence:

![](https://files.readme.io/2a8bc4f-Asset_69300x.png)

1. You generate the installation infrastructure and application configurations.
   1. The Configuration Generation process will interactively request the following inputs:
      1. Deployment environment=sandbox
      2. Execution phase=application installation
      3. Infrastructure provider=AWS
      4. Apple Push Notification token
      5. Authentication Service OpenID Connect Native App ClientID (Institutional Wallet Approver App)
      6. Authentication Service OpenID Connect Single-Page App ClientID (Wallet UI)
      7. Authentication Service OpenID Connect Audience
      8. Authentication Service OpenID Connect Issuer endpoint
      9. Crypto token rates key
      10. Ubiquity API key
      11. Initial Wallet admin user name and email
      12. Base64 encoded ERS public key
      13. 3x AWS Account IDs and region
   2. Execute the following to instantiate the Configuration Generation and output the configuration locally to the `mpa-wallet.yaml` within the local path:
      1. ```
         $ docker run -it -v $(pwd):/conf 638663786504.dkr.ecr.us-east-1.amazonaws.com/blockdaemon/wallet/installer:1.0.0
         ...
         ```
   3. The `mpa-wallet.yaml` configuration file includes autogenerated values for the following:
      1. mTLS key-pairs for authenticated and encrypted communication between MPA nodes.
      2. Default MPA Administration Policies.
      3. AWS infrastructure values with references to the secrets created as part of the key ceremony and seeding process.
      4. Helm deployment values for the application installation.
2. Adjust the `mpa-wallet.yaml` configuration values according to your setup needs.
   1. Refer to an example configuration with embedded explanations for each value [here](https://wallet.docs.blockdaemon.com/docs/mpa-self-installed-blockdaemon-wallet-sandbox-deployment-process-configuration-yaml-copy).
   2. Note the MPA node Administration Policies are not meant to be changed after setup and cannot be changed through the Wallet UI. These include policies for registering users, deleting users, changing transfer policies, assigning groups to a user, etc. Refer to the Administration Policies [here](https://wallet.docs.blockdaemon.com/docs/all-about-policies).
3. Initiate the infrastructure and application installation using the `mpa-wallet.yaml` in the current path.
   1. To synthesize and output the CloudFormation templates for later installation or use within pipelines:
      1. ```
         $ docker run -it -v $(pwd):/conf 638663786504.dkr.ecr.us-east-1.amazonaws.com/blockdaemon/wallet/installer:1.0.0
         ...
         ```
   2. To perform a diff against the current infrastructure state:
      1. ```
         $ docker run -it -v $(pwd):/conf 638663786504.dkr.ecr.us-east-1.amazonaws.com/blockdaemon/wallet/installer:1.0.0
         ...
         ```
   3. To perform an immediate installation using the synthesized templates:
      1. ```
         $ $ docker run -it -v $(pwd):/conf 638663786504.dkr.ecr.us-east-1.amazonaws.com/blockdaemon/wallet/installer:1.0.0
         ...
         ```
4. Finally, the administrator sets DNS name server zone delegations for the zone to the new AWS name servers.

## Step 9: Backup the wallet's master private key

Upon first logging in and pairing your account with the Institutional Wallet Approver App, approve backing up the wallet’s master private key from the Approver App. Ensures this backup is stored separately from the wallet system for use in recovery during a disaster.

Refer to the backup and process here: [Back Up Master Key](https://wallet.docs.blockdaemon.com/docs/back-up-master-key)
